### 5.3 Анализ коренных причин (Root Causes) в кодовой базе

1. **Асинхронный разрыв времени генерации (Generation Latency Gap):**  
   Полный цикл обработки клинического запроса (триаж + каскадный инференс LLM + RAG + валидация качества) занимает от **15 до 35 секунд**. Если пользователь при быстром наборе с мобильного устройства отправляет мысли отдельными короткими репликами (в данном случае через 16.5 секунд), вторая реплика входит в цикл обработки, когда первая еще находится на этапе генерации.
2. **Дедупликация только по единичному `msg_id`:**  
   В `assistant.py` защита от дублей строилась исключительно вокруг структуры `REPLIED_MSG_IDS.add(msg_id)`. Поскольку сообщения `177388` и `177389` имели разные идентификаторы Telegram, проверка не сработала. Межпоточный мьютекс (`asyncio.Lock`) или множество активных задач (`in_flight_threads`) отсутствовали.
3. **Обход флуд-контроля для режима диалога:**  
   В строке 2965 `assistant.py` существовала проверка:
   ```python
   if sender_id and not is_dialogue:
       if not check_user_cooldown(chat_id, sender_id, "group_trigger", seconds=8):
           return
   ```
   Условие `not is_dialogue` полностью отключало 8-секундный флуд-кулдаун для продолжающихся диалогов, делая бота абсолютно беззащитным перед дробным набором сообщений.
4. **Почему заблокировалось сообщение 177391:**  
   В `assistant.py` (строки 2800–2815) проверка продолжения кейса считает число сообщений `count_since <= 5` относительно опорного ответа `last_case_bot_msg` (`177385`):

   - Для сообщения `177389`: сообщения `[177386, 177387, 177388, 177389]` $\rightarrow$ `count_since = 4 <= 5` (Разрешено).
   - Для сообщения `177391` (в 17:27:20): бот уже записал в БД свой ответ `177390`! Список сообщений составил `[177386, 177387, 177388, 177389, 177390, 177391]` $\rightarrow$ `count_since = 6 > 5`!
