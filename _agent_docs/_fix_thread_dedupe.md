## Шаг 1. Механизм по каждой находке (чтение живого кода, до правок)

### 3a — гонка на протухшем состоянии

Реальная последовательность в `check_and_trigger_assistant`:

| строка | что делает |
|---|---|
| 1314 | `state = load_state()` — снимок состояния |
| 1442 | `passive_gate_block_reason(state)` — гейт кулдауна ПО ЭТОМУ снимку |
| 1466 | `reply_to_msg_id not in state.get("processed_threads", [])` — тоже по снимку |
| 1475 | `record_passive_attempt()` — первая запись на диск (10-мин backoff) |
| 1822 | `record_passive_success(pending_thread_id)` — полное окно + метка ветки |

Между 1314 и 1475 стоят await'ы: `database.get_last_n_messages` (1324),
`event.client.get_messages` — round-trip к Telegram (1352, срабатывает всегда,
когда `reply_to_msg_id` есть, а у этой ветки он есть по определению),
`query_db_async` на `has_media` (1460) и на `COUNT(*)` (1463).

`main.py:1637` — `runtime_guard.create_task(run_assistant_safe(), name=f"assistant_{msg_id}")`:
на КАЖДОЕ сообщение свой detached-таск, Telethon диспатчит апдейты конкурентно.
Значит два сообщения одной ветки — это два таска в одном событийном цикле,
и любой await отдаёт управление другому.

Итог: таск B делает `load_state()` до того, как таск A дошёл до
`record_passive_attempt()`, видит открытый гейт и пустой `processed_threads`,
и оба доходят до отправки. Два ответа в одну ветку.

Пассивная общая ветка частично прикрыта пере-чтением на 1509
(`passive_gate_block_reason(load_state())`), но и оно не спасает: свою запись
пассивная ветка делает только на 1570, то есть окно между 1509 и 1570 открыто
для обоих. Ветка клинического поста (1466) не пере-читает состояние вообще.

Диалоговый путь (`is_dialogue`) гейт не проходит и в гонке не участвует.

### 3b — обрезка `processed_threads` до 100

`record_passive_success` (`assistant.py:511-516`):
```python
        threads = state.setdefault("processed_threads", [])
        if thread_id not in threads:
            threads.append(thread_id)
            if len(threads) > 100:
                del threads[:-100]
```
Граница по ДЛИНЕ, не по возрасту. Ни строки в журнал: выброс молчаливый.
Проверка на 1466 — единственный потребитель этого списка; вылет записи
означает, что бот считает ветку неотвеченной и заходит в неё второй раз.

### 4b — `REPLIED_MSG_IDS` на текстовом пути

`REPLIED_MSG_IDS = TTLCache(maxsize=50000, ttl=604800)` (`assistant.py:37`).
Читается на 1828 (`check_and_trigger_assistant_media`, гард на входе),
пишется на 2096 (там же, после успешной отправки). В
`check_and_trigger_assistant` — ни чтения, ни записи: у текстового ответа
защиты «на это сообщение уже отвечали» нет вообще.

Практический зазор: одно и то же `msg_id` может пройти оба пути (снимок с
подписью), и медиа-гард текстовую отправку не видит, потому что текстовый путь
в кэш не пишет. Плюс `sync_history` (`main.py:2084`) прогоняет сообщение через
`handle_new_message` повторно, а `PROCESSED_MSG_IDS` (`main.py:44`, 500 записей
в памяти) после рестарта пуст.

## Шаг 2. Замеры

### Замер 1 — как часто ветка получает два почти одновременных ответа

Пары текстовых реплик к ОДНОМУ родителю (медиа-реплики `main.py` уводит в
медиа-ассистента, поэтому `has_media = 0` у обеих):

```sql
SELECT a.msg_id, b.msg_id, a.date, b.date, a.reply_to_msg_id,
       (julianday(b.date) - julianday(a.date)) * 86400.0 AS gap
FROM archive_messages a
JOIN archive_messages b
  ON a.reply_to_msg_id = b.reply_to_msg_id
 AND b.msg_id > a.msg_id
 AND (julianday(b.date) - julianday(a.date)) * 86400.0 <= :window
WHERE a.reply_to_msg_id IS NOT NULL
  AND COALESCE(a.has_media,0) = 0 AND COALESCE(b.has_media,0) = 0
  AND a.text IS NOT NULL AND b.text IS NOT NULL;
```

| окно | пар всего | из них гейт был ОТКРЫТ -> двойной ответ |
|---|---|---|
| 1 с | 77 | — |
| 2 с | 126 | **3** |
| 5 с | 319 | 5 |
| 10 с | 769 | 12 |
| 30 с | 2 678 | 54 |
| 60 с | 4 711 | **105** |
| 120 с | 7 187 | 157 |

«Гейт открыт» = хронологический реплей всего архива с обоими окнами
(`PASSIVE_COOLDOWN_MINUTES=120`, `PASSIVE_RETRY_MINUTES=10`) и
`processed_threads` с обрезкой до 100; первая реплика пары в этот момент
реально открывала ветку клинического поста.

Три пары в окне 2 с (то, что видно наверняка):
```
2025-04-11 14:22:59  #67951 || #67952 (+1.0 c)  тред #67946
2025-07-28 14:08:52  #87385 || #87386 (+1.0 c)  тред #87371
2026-01-30 11:54:45  #133181 || #133182 (+2.0 c) тред #133171
```

Честно про границу: длину окна гонки я НЕ измерял на живом боте — в `bot.log`
и `bot.log.1` нет ни одной строки `Triggered assistant`, ассистент в этих
журналах не срабатывал, замерить round-trip к Telegram нечем. Поэтому
0.003/сутки (окно 2 с) — это нижняя граница, 0.10/сутки (окно 60 с) — оценка
при медленном round-trip. Точная частота между ними, и она неизвестна.

### Замер 2 — за сколько суток проедаются 100 записей `processed_threads`

Хронологический реплей ветки клинического поста, точный повтор кода:

```sql
-- вход реплея: все сообщения по хронологии
SELECT msg_id, date, text, reply_to_msg_id, COALESCE(has_media,0) AS has_media
FROM archive_messages ORDER BY date ASC, msg_id ASC;
```
плюс в питоне: счётчик ответов на родителя нарастающим итогом (эквивалент
`SELECT COUNT(*) FROM messages WHERE reply_to_msg_id = ?` на момент реплики),
`has_media` родителя, оба окна кулдауна, `processed_threads` с `del threads[:-100]`.

| | шт |
|---|---|
| кандидатов (`reply_count>=3`, родитель с медиа) | 4 075 |
| подавлено `processed_threads` | 1 360 |
| отправок (верхняя граница) | 891 = **0.88/сутки** |
| выброшено обрезкой МОЛЧА | **791** |
| ПОВТОРНЫХ входов в уже отвеченную ветку | **20** |

Срок памяти о ветке (от попадания в список до вылета):

| перцентиль | суток |
|---|---|
| p5 | 54.9 |
| p25 | 63.4 |
| p50 | **104.0** |
| p75 | 148.3 |
| p95 | 208.2 |
| минимум | **52.0** |
| средний | 115.1 |

То есть бот забывает отвеченную ветку в среднем через 115 суток, в худшем
случае через 52.

Тот же реплей без обрезки: 872 отправки, **0** повторных входов. Обрезка до 100
добавляет ровно 20 лишних вторжений.

Разрыв между первым и повторным вторжением: мин 75.6 / медиана 223.7 / макс
810.2 суток. Примеры:

### Замер 3 — сколько живёт ветка (чтобы окно хранения её накрывало)

```sql
SELECT p.msg_id, COUNT(r.msg_id) AS n,
       julianday(MAX(r.date)) - julianday(MIN(p.date)) AS span_days
FROM archive_messages p
JOIN archive_messages r ON r.reply_to_msg_id = p.msg_id
WHERE COALESCE(p.has_media,0) = 1
GROUP BY p.msg_id HAVING COUNT(r.msg_id) >= 3;
```
1 028 таких веток. Жизнь ветки: p50 = 0.26 сут, p75 = 1.9, p90 = 14.0,
p95 = 57.1, p99 = 339.2, максимум 820.0.

Важнее хвост ПОСЛЕ третьего ответа — с этого момента бот может влезть, и
именно этот отрезок должен целиком лежать внутри окна хранения:

| перцентиль | суток |
|---|---|
| p50 | 0.024 |
| p90 | **9.7** |
| p95 | **37.5** |
| p99 | **281.7** |
| максимум | 810.2 |

Веток с хвостом > 30 суток — 56 из 1 028, > 90 суток — 32.

Сколько записей нужно, чтобы удержать окно по возрасту (замер по реплею):
30 сут -> 62 записи, 90 сут -> 166, 180 сут -> 304, **365 сут -> 507**.

Вывод для правки: окно 365 суток накрывает p99 хвоста (281.7) и снимает 19 из
20 измеренных повторов; предел по размеру достаточно поставить сильно выше 507,
чтобы в норме он не срабатывал никогда.

## Шаг 3. Правки в `assistant.py`

### 3a — заявка на слот незваного ответа (не sleep, не блокирующий замок)

Новое, рядом с `passive_gate_block_reason`:
`_PASSIVE_CLAIMS` (`ключ -> (таск-владелец, время взятия)`),
`PASSIVE_CLAIM_TTL_SECONDS = 600`,
`claim_passive_slot(key)` — берёт заявку или ОТКАЗЫВАЕТ (не ждёт),
`_release_claims_of_task(task)`,
`_drop_stale_passive_claims()` — снимает заявки завершившихся владельцев и
протёкшие по TTL, с `logger.warning`.

Заявка берётся в двух местах `check_and_trigger_assistant`: в ветке клинического
поста (сразу после `reply_count >= 3 and ... not in processed_threads`) и в общей
пассивной ветке (после `not is_obviously_junk and not passive_cooldown_active`).
Диалоговый (приглашённый) путь заявку НЕ берёт — подавить прямой вопрос врача
хуже, чем два незваных ответа.

Ключ ОДИН и общий, `("passive_text",)`. Сначала я поставил вторым ключом
`("thread", reply_to_msg_id)`, но диверсия показала, что он не несёт ничего:
`last_passive_text_run` и `processed_threads` — глобальные ключи состояния, одно
окно на весь чат, поэтому заявка по ветке в поведении неотличима от общей.
Убрал: это была бы ровно та мёртвая защита, от которой мы избавляемся в 4b.

Снятие привязано к завершению таска (`task.add_done_callback`), а не к явному
вызову. Причина: после места заявки у функции ОДИННАДЦАТЬ точек выхода (отказ
триажа, `not triggered`, пустой корпус, ошибка Gemini, пустой текст, IGNORE,
отказ рецензента, два успеха, два провала отправки). Ставить release на каждую —
гарантированно потерять одну при следующей правке, а необработанное исключение
между ними не покрыть вообще. `main.py:1637` создаёт на каждое сообщение
отдельный таск (`create_task(run_assistant_safe(), name=f"assistant_{msg_id}")`),
поэтому колбэк отрабатывает сразу после ответа и на ЛЮБОМ исходе — return,
исключение, отмена. Проверены все три случая, секция [3] теста.

Почему не `try/finally` вокруг тела: обёртывание потребовало бы переотбить ~360
строк, а вынести тело в `_impl` нельзя — `test_silence_all_paths.py:85` и
`test_validator_coverage.py:73` разбирают через `ast` тело именно функции с
именем `check_and_trigger_assistant`, и тонкая обёртка их бы уронила.

### 3b — `processed_threads` по возрасту

- `PROCESSED_THREAD_TTL_DAYS = 365` — покрывает измеренный p99 хвоста 281.7 сут;
- `PROCESSED_THREADS_MAX = 2000` — вторичная граница (на 365 суток нужно 507
  записей, значит в норме не срабатывает);
- `processed_thread_dates` в `STATE_DEFAULTS`, вид `{"12345": iso}`. Отдельным
  словарём, чтобы `processed_threads` остался списком id: проверка на 1466 и
  файлы состояния на диске работают без миграции;
- `_prune_processed_threads(state, add=None)` — чистка по возрасту, затем по
  размеру, затем запись обеих структур;
- `record_passive_success` зовёт её вместо `del threads[:-100]`.

Журнал: выброс по возрасту — `logger.info` с числом и номерами веток (до 20);
обрезка по размеру — `logger.warning` со словом `still-fresh` и номерами, потому
что это выброс ещё актуальных веток и после него бот может влезть в них снова.
`info`, а не `debug`: корневой уровень журнала INFO, `debug` не эмитится — на
этом уже попался кулдаун (0 строк на 126 340).

Ветка без метки (старый файл состояния) считается увиденной СЕЙЧАС и стареет с
этого момента: иначе первая чистка сожгла бы всю историю и бот разом вернулся бы
во все отвеченные ветки. Метка существующей ветки на чистке НЕ освежается, иначе
запись не постарела бы никогда.

### 4b — `REPLIED_MSG_IDS` сделан несущим, не удалён

Выбор: кэш не бесполезен — он уже единственный гард медиа-разбора
(`check_and_trigger_assistant_media`, гард на входе плюс запись после отправки),
и симметрия нужна именно чтобы этот гард видел текстовые отправки. Удаление
сняло бы работающую защиту медиа-пути ради чистоты; цена несущего варианта —
пять строк.

- чтение: в начале `check_and_trigger_assistant`, сразу после отсева команд,
  с `logger.info`;
- запись: на всех четырёх путях, где функция возвращает `True` (извинение из
  `check_and_apply_silence`, извинение в диалоге, shadow-отправка, живая
  отправка). Все четыре реально что-то отправили, то есть `True` = «мы говорили».

Чего это НЕ лечит, честно: оба кэша (`REPLIED_MSG_IDS` и `PROCESSED_MSG_IDS` в
main.py) живут в памяти процесса, рестарт снимает оба. Закрывается
внутрипроцессный зазор: повторная подача того же `msg_id` через
`sync_history`/`handle_new_message` и двойной ответ на снимок с подписью
(текстовый путь плюс медиа-путь). Межрестартный зазор требует метки в базе —
это правка `database.py`/`main.py`, не моя.

## ПРАВКА ДЛЯ ЛИДА: `test_passive_gate.py` (файл не мой)

Строки 100-104 закрепляют снятую границу по длине и падают:
`[FAIL] список ограничен 100 -- got 151`. Это ожидаемо: 151 свежая ветка теперь
не режется, потому что граница по возрасту. Предлагаемая замена строк 100-104:

    reset(processed_threads=list(range(150)))
    A.record_passive_success(thread_id=999)
    threads = A.load_state()["processed_threads"]
    check("свежие ветки не режутся до сотни", len(threads) == 151, f"got {len(threads)}")
    check("свежий тред сохранён", 999 in threads)
    check("граница по возрасту, а не по длине",
          A.PROCESSED_THREAD_TTL_DAYS >= 282 and A.PROCESSED_THREADS_MAX > 507)

Обоснование числа 282: измеренный p99 хвоста обсуждения после третьего ответа —
281.7 суток. Всё, что короче, возвращает бота в ещё живую ветку.
