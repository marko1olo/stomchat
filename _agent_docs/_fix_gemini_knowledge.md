## 2. Замер молчаливости ДО правки (поведенческий, сеть заглушена)

Скрипт `_probe_silent.py`: подменяет `gemini_knowledge.genai` на фальшивый
клиент, вешает handler на `gemini_knowledge.logger`, считает строки журнала и
фактически ушедшие запросы. Сети нет, боевые базы не открываются.

| сценарий ответа модели | что вернула функция | запросов | строк в журнале |
|---|---|---|---|
| `response.text = ""` | `None` | 3 | **0** |
| `response.text = None` | `None` | 3 | **0** |
| 404 по всем ключам (модель снята) | `None` | 3 | **0** |
| мусор `s: ["MSG_2421", ...]`, `c: "2.3.2, 2.3.1"` | мусор отдан как есть | 1 | **0** |
| прозаический отказ вместо JSON | проза отдана как есть | 1 | **0** |
| валидный JSON | JSON | 1 | 0 |

Ключевое: `response_mime_type` во ВСЕХ ушедших запросах — `None`. Ветка
`if not is_gemma` мертва не по чтению кода, а по замеру: `models_to_try` содержит
одну `models/gemma-3-27b-it`, JSON-режим не включался ни разу.

Второе ключевое: **отказ полностью бесшумен**. 404 по всем 10 ключам (модель снята
с обслуживания) даёт `None` и НИ ОДНОЙ строки в журнале — виновата ветка
`if "404" not in err`, которая глотает именно тот случай, когда синтез знаний
умирает целиком. Для врача это выглядит так: вики просто перестаёт расти, и
в журнале об этом ни строки.

Живые журналы подтверждают, что путь рабочий и молчание не теоретическое:
в `distiller.log` 33 строки `Rate limit for` (ветка 429 со сном 10 с реально
срабатывала) и 1 строка `Error models/gemma-3-27b-it: server disconnected`.
Строк `Провал парсинга JSON` — 0, то есть непригодные ответы уходили в базу
разобранными, а не отвергнутыми.

## 3. Что решено делать (обоснование выбора)

Бриф предлагал три варианта; беру все три, потому что по одиночке каждый
недостаточен, и добавляю дедлайн вызова.

1. **Fallback-модель с `response_mime_type='application/json'` + `response_schema`.**
   Только схема лечит оба дефекта в корне: `s` объявляется массивом INTEGER
   (ярлык `MSG_2421` перестаёт быть выразимым), `c` — строкой (склейка списка в
   `'2.3.2, 2.3.1'` перестаёт рождаться на стороне модели). Одного
   `response_mime_type` мало: он даёт синтаксис JSON, но не контракт полей.
2. **Проверка `finish_reason` и пустого ответа с громким отказом.** Закрывает
   строки 1-3 таблицы выше: обрезка по `max_output_tokens` и пустой кандидат
   больше не выглядят как «модель промолчала».
3. **Валидация разобранного ДО возврата.** Гемма остаётся в цепочке последней
   (она сейчас единственная рабочая), JSON-режима не поддерживает, и её ответ
   надо проверять руками.

Политика трёх исходов вместо «вернуть что дали»:

- **принять** — ответ разобрался и контракт соблюдён → вернуть немедленно;
- **запомнить** — ответ не разобрался как JSON (типично обрезка) → попробовать
  следующего кандидата, но если лучше ничего не пришло, всё равно вернуть, потому
  что `distiller.parse_facts` умеет спасать целые объекты фактов из обрезанного
  ответа, и рубить эту возможность нельзя;
- **отвергнуть насовсем** — ответ разобрался, но `s` в ярлыках или `c` списком.
  Такой ответ не отдаётся никогда, даже как последняя надежда.

Почему отказ безопаснее записи мусора: `distiller.py:876` обрабатывает
`no_response` и `parse_error` ОДИНАКОВО — пачка не выжигается, а повторяется до
`MAX_BATCH_ATTEMPTS = 3`, и только потом уходит в журнал строкой `ПОТЕРЯ` с
диапазоном msg_id. То есть цена отказа — видимая дыра в журнале с точным
диапазоном реплик. Цена молчаливой записи — 353 факта в вики, у которых врач не
может открыть ни одного исходного сообщения. Вторая цена выше.

**Дедлайн вызова.** Проверено: родительского дедлайна нет —
`distiller.process_batch` зовёт `run_in_executor` без таймаута, а единственные
таймауты в `distiller.py` это `aiosqlite.connect(timeout=30)`. Худший случай ДО
правки: 10 ключей x 10 с сна на 429 = ~100 с. Цепочка из трёх моделей без
дедлайна дала бы ~300 с, то есть я бы втрое ухудшил то, чего не просили. Поэтому
весь вызов ограничен `_CALL_DEADLINE_SECONDS = 120`, проверка стоит и перед
попыткой, и перед сном; вложенность соблюдена тем, что мой дедлайн — внешний и
единственный, и он держится в порядке прежнего худшего случая.

## 4. Правка

`gemini_knowledge.py`: 74 -> 232 строки. Изменения:

- `_FACTS_SCHEMA` — схема ответа: `facts[].s` = массив INTEGER,
  `facts[].c` = STRING, `f` = STRING, `case` = BOOLEAN.
- `_models_to_try()` — цепочка: сначала JSON-моделі (`config.GEMINI_KNOWLEDGE_MODELS`,
  если оператор задал, иначе `gemini-2.0-flash`, `gemini-2.5-flash`), последней
  `models/gemma-3-27b-it`. Дедупликация с сохранением порядка. Гемма ОСТАЛАСЬ в
  цепочке: она сейчас единственная проверенно рабочая, и если новые id окажутся
  недоступны, поведение вырождается в сегодняшнее плюс строка в журнале.
- `_finish_reason(response)` — достаёт `candidates[0].finish_reason` терпимо к
  форме (enum/строка/отсутствие).
- `validate_fact_payload(text)` -> `(verdict, reason)`, где verdict это
  `"ok" | "unparsed" | "contract"`. Проверяет: `s` только целые (int или строка
  из цифр); `c` не список и без запятой; в каждом факте есть непустой текст.
- В теле `generate_fact_json`: JSON-режим для не-gemma моделей включён (ветка
  ожила), пустой ответ и `finish_reason` логируются громко, 404 больше не
  глотается, финальный `return None` сопровождается строкой `СИНТЕЗ НЕ СОСТОЯЛСЯ`
  с перечислением причин по кандидатам.

Комментарии в коде названы последствием для врача, не описанием кода.

## 5. Проверка после правки

### Свой тест: `test_gemini_knowledge_json.py`

`python test_gemini_knowledge_json.py` -> **PASSED: 57   FAILED: 0**, exit 0.
Сеть не задействована: `genai.Client` подменён, `assert` внутри фальшивого
клиента падает, если в него попадёт не `fake-key`. Часы подменены `FakeClock`,
поэтому проверки дедлайна детерминированы и не флакуют под параллельной
нагрузкой (тайминговый флак исключён конструкцией, а не усреднением).

#### Первый прогон нашёл дефект В САМОМ ТЕСТЕ (41 PASS / 1 FAIL)

Проверка «дедлайн или отмена сна названы в журнале» падала, и падала
СПРАВЕДЛИВО — не из-за продакшн-кода. Блок [10] гонял 429 на трёх фальшивых
ключах: 3 модели x 3 ключа x 10 с = 90 с, что в дедлайн 120 с влезает, ветка
дедлайна не исполняется, и строки в журнале законно нет. То есть проверка
требовала следствия от ветки, которую сама же не запускала.

Замер боевого масштаба: `len(config.GOOGLE_KEYS) == 10`, значит худший случай
3 модели x 10 ключей x 10 с = **300 с против дедлайна 120 с** — в бою ветка
срабатывает, на трёх ключах никогда. Блок [10] переписан на боевые 10 ключей;
добавлены две проверки, которых не было: дедлайн должен ОБОРВАТЬ каскад
(`len(reqs) < 30`), и на трёх ключах он НЕ должен срабатывать досрочно — иначе он
рубил бы здоровый перебор ключей и пачка уходила бы в отказ при живой квоте.
Это и есть та ошибка масштаба, из-за которой «зелёный» тест мог сторожить
неработающий дедлайн.

Оба обязательных случая из брифа закрыты поведенчески, не по тексту исходника:

- валидный JSON — блок [1]: функция возвращает ответ, и в ушедшем запросе
  реально стоит `response_mime_type='application/json'` плюс `response_schema`
  (проверяется перехваченный `config`, а не наличие строки в файле);
- мусор с `MSG_` — блок [3]: возврат `None` + строка `ОТКАЗ` в журнале + причина
  называет и провенанс, и склейку кода.

## 5a. НОВЫЙ ДЕФЕКТ, внесённый правкой прошлой волны, и его исправление

Правка прошлой волны поставила две новые модели ПЕРЕД Gemma под общим дедлайном
120 с — и этим создала голодание единственной проверенно рабочей модели.

Замер (`_probe_gk_starvation.py`, `_probe_gk_starvation2.py`, боевые 10 ключей,
сети нет, часы подменены): новые JSON-модели отдают 429 на всех ключах, Gemma
работает и ответила бы. Сон 10 с на каждый 429 съедает весь бюджет.

| латентность запроса | до правки: до Gemma дошло | до правки: результат | после правки |
|---|---|---|---|
| 0.0 с | ДА | факты доехали (120.0 с) | факты доехали (90.0 с) |
| 0.5 с | ДА | факты доехали (116.5 с) | факты доехали (96.0 с) |
| 1.0 с | ДА | факты доехали (112.0 с) | факты доехали (91.0 с) |
| **2.0 с** | **НЕТ** | **ОТКАЗ (122.0 с)** | факты доехали (90.0 с) |
| **5.0 с** | **НЕТ** | **ОТКАЗ (125.0 с)** | факты доехали (105.0 с) |

При нулевой латентности до Gemma доходило только потому, что сравнение строгое
(`now > deadline`, ровно 1120 > 1120 ложно) — то есть проходило по границе
случайно. С реальным сетевым временем от 2 с очередь до Gemma не доходит НИ РАЗУ,
и пачка уходит в отказ, хотя рабочая модель в списке есть. Последствие для врача:
статьи не появляются не из-за отсутствия рабочей модели, а из-за того, что её
место в очереди выел сон на чужой исчерпанной квоте.

Правка: `_LAST_RESORT_RESERVE_SECONDS = 25` — ранние модели живут по мягкому
дедлайну `deadline - резерв`, последняя по общему. Бюджет вложен: мягкий дедлайн
строго меньше общего, новых внешних таймаутов не появилось. Побочно стало лучше и
по времени: 90-105 с против 111-125 с.

### Диверсия, которую тест НЕ заметил с первого раза (важнее гладкого отчёта)

«Пустой ответ модели снова без строки в журнале» — я заменил `logger.error` на
`pass`, и тест остался **зелёным (45/0)**. Причина найдена замером журнала:
подстрока `пустой ответ` попадает в журнал ДВАЖДЯ — из строки про конкретную
модель и из итоговой `СИНТЕЗ НЕ СОСТОЯЛСЯ ... Причины: ...`, потому что причины
собираются из того же текста. Проверка `any("пустой ответ" in m)` получала
подстроку из итоговой строки и не замечала, что диагностика по моделям исчезла
целиком.

Это тот самый класс «проверка выглядит поведенческой, а удовлетворяется чужим
путём кода». Исправлено: якорь на фразу-последствие `не даст ни одного факта`,
которая есть ТОЛЬКО в строке про модель, плюс проверка КОЛИЧЕСТВА таких строк —
по одной на попытку. Тем же классом была больна проверка 404 (`any("404" in m)`
