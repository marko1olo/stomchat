## Шаг 1. Механизм находки 1 (по чтению, без запуска)

Догон офлайн-окна: `main.py sync_history()` (строка 1928 до правок).

1. `last_id = database.get_last_msg_id()` = `MAX(msg_id)` (`database.py:510`).
2. `client.iter_messages(SOURCE_CHAT_ID, min_id=last_id, reverse=True)` — окно.
3. На каждое сообщение: `database.save_message(..., text=message.message or "", has_media=has_media,
   media_type=media_type)`, где `media_type = clinical_media_kind(message)`.
4. `clinical_media_kind` (`media_tools.py:178`) отдаёт только `"photo"`, `"video"` или `None`.
   Для голосового — `None`, потому что это НЕ клинический снимок. Значит `has_media = False`.
5. Из-за `has_media = False` голосовое не попадает:
   * ни в `synced_singles` / `synced_albums` (постановка в очередь разбора идёт под `if has_media:`),
   * ни в `recover_pending_media_analysis`: `database.get_pending_media_message_ids`
     (`database.py:670`) выбирает `WHERE has_media = 1 AND (media_description IS NULL OR = '')`.
6. `transcribe_group_voice` в `sync_history` не вызывается ни разу.
7. Единственный шанс — хвост: `if count > 0 ... last_synced_message` прогоняется через
   `handle_new_message` (строки 2064-2084), и только если его id не в `already_enqueued`.
   То есть расшифровку получает РОВНО ОДНО голосовое окна — последнее сообщение окна, и только
   если последним оказалось именно голосовое.

Итого: механизм — не «теряется по таймауту», а «в догоне расшифровки нет вообще»; последнее
сообщение окна спасает случай, а не замысел. Восстановить пост-фактум нечем: строка голосового в
базе (`text=''`, `has_media=0`, `media_type=NULL`) неотличима от стикера или пустого сообщения.

Второй слой того же: строка пишется ДО расшифровки (`main.py:1427` идёт после `save_message`),
поэтому падение процесса на скачивании/Whisper теряет расшифровку окончательно — `get_last_msg_id`
уже включает это голосовое, а `iter_messages(min_id=last_id)` его исключает.

## Шаг 5. Правка (внесена в `main.py`)

Новое состояние и константы:

* `_TRANSCRIBED_MSG_IDS` / `_TRANSCRIBED_ORDER` (deque maxlen=512) + `_remember_transcribed` —
  одно голосовое не уезжает в Whisper дважды; отдельно от `PROCESSED_MSG_IDS`, который считает
  апдейты. (`_remember_queued_media` рядом не тронута: её последняя строка
  `_QUEUED_MEDIA_IDS.add(queued_id)` сохранена на месте.)
* `VOICE_ITEM_OVERHEAD_SECONDS = 45` (запас подпроцесса 10 + правка терминов 20 + файловые
  операции), `VOICE_ITEM_BUDGET_SECONDS = 120 + 60 + 45 = 225` — из слагаемых, не числом.
* `VOICE_BACKLOG_MAX_ITEMS = 10` (`STOMCHAT_VOICE_BACKLOG_MAX`),
  `VOICE_BACKLOG_MIN_ITEM_SECONDS = 15`,
  `VOICE_BACKLOG_TOTAL_SECONDS = max(2 × 225, STOMCHAT_VOICE_BACKLOG_SECONDS=1800) = 1800`.
  Вложенность: `MIN < ITEM < TOTAL`, и на каждое голосовое берётся
  `min(VOICE_ITEM_BUDGET_SECONDS, остаток)`, поэтому внутренний срок не может пережить внешний.
* `VOICE_FAILURE_SILENCE`, `VOICE_UNRECOGNIZED_MARK`.

Функции:

* `is_voice_message(message)` — одно правило для живого пути и для догона.
* `transcribe_group_voice` теперь возвращает `(текст, причина_отказа)`; шесть тупиков различимы,
  «тишина» отделена от «наш отказ». Отмена (`CancelledError`) пропускается наружу.
* `_publish_voice_transcription`, `_notify_voice_failure` — публикация и одна строка на отказ.
* `_store_voice_text(msg_id, text, repair=None)` — ПРОВЕРЯЕТ rowcount, при 0 пишет
  `VOICE TEXT NOT PERSISTED` и восстанавливает строку через `save_message` (INSERT OR IGNORE).
* `_mark_voice_unrecognized(messages, reason)` — отметка в базе, непустой текст не затирает.
* `transcribe_voice_backlog(messages, source)` — догон с двумя пределами и журналом отброшенного.
* `sync_history`: собирает `synced_voices`, отдаёт их отдельной задачей
  `runtime_guard.create_task(...)` (внутри 900-секундного бюджета синхронизации этого делать
  нельзя — подъём падал бы по таймауту), и добавляет их id в `already_enqueued`, чтобы
  `handle_new_message` не расшифровал последнее голосовое вторым платным вызовом.
