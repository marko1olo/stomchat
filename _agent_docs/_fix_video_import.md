## Для лида

**1. Миграция UNIQUE. Проверена на ВРЕМЕННОЙ копии боевых данных, в боевую базу не вносилась.**
UNIQUE-индексов нет ни одного, поэтому `INSERT OR IGNORE` в `videosi.py` сейчас не отсекает ничего
— дубли держит только Python-проверка, и она не спасёт от двух одновременных прогонов на разных
машинах. Узкий индекс по номеру протокола, а не по тексту факта:

    ALTER TABLE distilled_facts ADD COLUMN protocol_msg_id INTEGER;
    UPDATE distilled_facts
       SET protocol_msg_id = CAST(substr(content,
                                         instr(content, 'MSG ') + 4,
                                         instr(content, ']') - instr(content, 'MSG ') - 4) AS INTEGER)
     WHERE content LIKE '%ВИДЕО-ПРОТОКОЛ | MSG %';
    CREATE UNIQUE INDEX IF NOT EXISTS idx_protocol_msg_id ON distilled_facts(protocol_msg_id);

Мой замер на копии (53 настоящих видео-факта + 200 настоящих обычных, `_measure_video_unique.py`):

- `protocol_msg_id` заполнился у **53 из 53**, номера разобраны верно (1271, 1275, 1276, 1279...),
  мусора **0**;
- у 200 обычных фактов `NULL`, и **множественные NULL уникальности не нарушают** — проверено;
- повторный `INSERT OR IGNORE` того же протокола: было 253 строки, стало 253 — **отсекла база**;
- без `OR IGNORE`: `IntegrityError: UNIQUE constraint failed: distilled_facts.protocol_msg_id`;
- повторный `ALTER` -> `duplicate column name`, оборачивать как в `reclass.ensure_schema`;
- цена: узкий индекс копеечный, а `UNIQUE(content)` добавил **+593 920 байт на 253 фактах** —
  в пересчёте на 12 784 факта порядка 29 МБ к базе на 9 МБ. По тексту индексировать не стоит.

**После миграции `videosi.py` нужна правка на две строки** — `protocol_msg_id` в список колонок
INSERT и `msg_id` в параметры (`videosi.py:196-200`). САМ НЕ СДЕЛАЛ намеренно: на
непромигрированной боевой базе такой INSERT упал бы `no such column`, и импорт не записал бы ни
одного протокола. Это правка «после миграции», а не «вместе с ней».
